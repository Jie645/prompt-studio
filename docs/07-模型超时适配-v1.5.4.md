# 模型超时被误判为「模型不可用」（v1.5.4）

## 1. 现象

两张截图，同一个根因：

- **提示词优化工作台**：「开始优化」后，状态栏红字 `模型不可用，已生成离线结构版：整轮超时：超过 60 秒`，结果框里是离线规则生成的 2110 字结构版。
- **生成结果页**：`3 / 3 步全部完成 · 已按 5 轮回答补全 · 模型调用失败 · 已回退离线规则`，橙色警示条 `整轮超时：超过 60 秒。已自动改用离线规则出稿`，分数卡仍按离线稿打出 93 分。

两处都不是模型真的不可用，而是**整轮上限被固定成了 60 秒**。

## 2. 根因

```js
var capMs = Math.max(20000, Math.min(timeoutMs(), NET.hardCap));   // timeoutMs() = 设置里的「响应超时」
```

`timeoutMs()` 直接取设置面板的「响应超时」（默认 60s，可选 30/60/120）。这个值被当成**整轮**硬上限，而输出预算默认 1600 tokens、详尽档 2600、推理模型下限 8192：

| 输出预算 | 按 18 token/s 估算所需时间 |
| --- | --- |
| 1600 tokens | ≈ 89s |
| 2600 tokens | ≈ 144s |
| 8192 tokens（推理模型） | ≈ 455s |

也就是说，**60 秒的上限和默认输出预算在算术上就不匹配**：只要模型慢一点，或者先思考再输出正文（推理模型思考期间 `partial` 为空），必然在 60 秒被 abort。推理模型的思考阶段还会先占用一段时间，60 秒内连一个字都到不了正文，于是「已收到内容」也为空，只能整体回退离线规则。

同时文案把「超时」写成「模型不可用」，把可以正常调用的模型说成坏的，误导排查方向。

## 3. 修复内容

### 3.1 整轮上限按输出预算自适应

新增 `roundCapMs(tokens)`：

```js
function roundCapMs(tokens) {
  var t = Number(tokens) || 1200;
  var need = 12000 + Math.round((t * 1000) / 18);   // 12s 首字/网络余量 + 18 token/s 的正文时间
  return Math.min(Math.max(timeoutMs(), need), NET.hardCap);   // 最长 300s
}
```

- 调用点改为 `capMs = roundCapMs(opts.maxTokens || budgetOf())`
- 设置里的「响应超时」变成**下限/基准**，不再把大预算请求钉死在 60 秒
- 首字等待随整轮上限放大（`min(capMs - 15s, 120s)`），非流式网关不再被 59 秒误杀
- 中途空闲（18s 没有任何字节）仍旧立刻止损，慢不等于无限等

### 3.2 文案不再把超时说成「模型不可用」

- 优化工作台错误前缀按原因区分：`模型响应超时，已生成离线结构版：…` / `模型调用失败，已生成离线结构版：…`
- 提示里的秒数取实际生效上限（如「超过 101 秒」），不再是固定的 60
- 设置项说明改为：「基准超时 Xs：整轮会按输出上限自动放宽（最长 300s），首字最多等 120s；确实没写完才回退离线规则」
- 追问阶段的「已等待 Xs · 上限 Ys」显示实际生效值

## 5. 已知限制

- 300 秒是硬上限（`NET.hardCap`）；真正跑满 300 秒仍没写完的模型，还是会回退离线稿
- 每 18 秒没有任何字节的流会被判定为卡死并中止，这是有意保留的止损
- 本次只改超时与文案，未改动生成逻辑、评分算法与界面布局
